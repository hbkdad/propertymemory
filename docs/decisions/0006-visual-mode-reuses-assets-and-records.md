# ADR 0006: Visual property mode reuses `assets`/`records`; only the pin itself is new

## Status
Accepted

## Context
The visual/spatial navigation upgrade (property → room → wall/fixture → knowledge) needs: photos attached to a room, clickable regions on those photos ("hotspots"), and, behind each hotspot, whatever is known about the thing it points to (a wall's paint, a cabinet, a furnace) plus its history. The product brief's own sketch of this (Section 40 of the upgrade spec) lists a dozen plausible new tables — `property_media`, `room_media`, `visual_annotations`, `materials`, `finishes`, `components`, `component_relationships`, `historical_media` — but explicitly warns not to create them blindly and to reuse what already fits.

## Decision
- **Photos are `attachments`, not a new media table.** A room/property photo is still exactly "a file with an owner" — the same thing a receipt or a warranty PDF already is. `attachments` gains `space_id` (a 5th owner alongside property/asset/record/warranty), a `role` (`document` | `photo`), `is_cover`, `sort_order`, and `width_px`/`height_px` (so hotspot math and layout don't have to wait on the image to load). No new table, no new Storage bucket, no new RLS policy shape — the existing `is_org_member(organization_id)` policies and the existing storage.objects bucket policy (keyed on the same org-id path prefix) already cover it.
- **A hotspot points at an `asset`, not a new "component"/"material".** `assets` already has exactly the shape this needs — `manufacturer`, `model_number`, `serial_number`, `installed_on`, `purchased_on`, `purchase_price`, `vendor_id`, and an optional `space_id` — and it already fits a furnace or dishwasher without question. The reframe this ADR makes explicit: a wall's paint, a run of cabinets, a roof, and a tile floor are the same kind of thing — a physical, trackable item with acquisition/install info — not a structurally different concept that needs its own table. Two new `asset_categories` rows (`cabinetry`, `tile`) cover the gaps; `roofing`/`exterior`/`flooring`/`painting` already existed.
- **History is `records`, not a new versioning table.** "2025 repainted, 2021 previous colour" is precisely what ADR 0005 already built `records` for — a `record_type` of `material` (`Paint / Material`, already seeded) scoped to `asset_id`, ordered by `occurred_on`. No new table.
- **The only genuinely new concept is `visual_annotations`** — the pin itself: which photo, what shape (`point`/`rectangle`/`polygon`), normalized (0–1) coordinates, a label, and an optional `asset_id` it points to. Nothing in the existing schema has this shape (a spatial region on an image), so it earns its own table. `asset_id` is nullable — a hotspot can exist before it's linked to a fully-detailed asset (see Section 46 of the upgrade spec, "visual association" must stay separate from "domain entity": deleting a pin never deletes the asset it points to, and this table only ever reads `assets`/`attachments`, never the reverse).
- **Reusable material definitions (Section 43 — "White Dove OC-17 used in 3 rooms, edit once") are deliberately deferred**, not built now. That's a real feature but a later one: today, two different walls painted the same colour are two separate `assets` with duplicated fields, which is a real but acceptable cost until a second/third case actually demands central tracking — consistent with CLAUDE.md's rule against speculative abstraction.

## Alternatives considered
- **A parallel `room_media`/`materials`/`components` subsystem** (the brief's own first-draft sketch): rejected after inspecting the existing schema — it would duplicate RLS, storage policy, and CRUD UI that `attachments`/`assets`/`records` already have working and tested, for no shape difference that actually matters yet.
- **Storing a hotspot's descriptive fields directly as JSON on `visual_annotations`** instead of linking to a real `asset`: rejected — it would mean "things you can click on a photo" and "things in your asset list" silently diverge into two untracked inventories of the same physical items, defeating the point of a property *memory*.

## Consequences
- Adding a hotspot for something that isn't in the asset list yet requires creating that asset first (or inline, in the same flow) — this is a feature, not friction: it means the visual view and the structured records view are always looking at the same underlying data, never a shadow copy.
- If reusable material definitions are ever built, `assets` rows for painted surfaces are the natural migration source (group by manufacturer + model_number + colour), not a parallel dataset to reconcile.
- `visual_annotations.asset_id on delete cascade` means deleting an asset silently removes any pin pointing to it — acceptable since a pin with nothing behind it is meaningless, but worth remembering if "soft delete" for assets is ever added later.
